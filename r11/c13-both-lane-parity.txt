HOW LANE-ON WAS MADE DRIVABLE (reversible; restored — see foot of file)
     The dormant endpoint-asset-ingestion deployment shipped no LaunchDarkly SDK
     key (config.yaml had no feature_flags section; deployment env only wired
     ONYX__DATABASE__* + aws-credentials), so its LD client never initialized and
     the consumer could not evaluate flag-ON. Reversibly patched the deployment to
     inject ONYX__FEATURE_FLAGS__LAUNCHDARKLY_SDK_KEY from secret
     launchdarkly-sdk-key/sdk-key and scaled it up; the pod logged
     "Started LaunchDarkly Client: OK". The dev fallthrough for
     endpoint-asset-ingestion is variation 0 = true, so an initialized consumer
     evaluates flag-ON for any tenant. No LD targeting rule was added or flipped.

ATTRIBUTION NOTE (why the lane-ON write is the consumer's, not Temporal's)
     The shared ingestion bucket fans every ObjectCreated to ALL per-source
     queues (scanner-events, endpoint-asset-ingestion, ...), and
     temporal-scanner-worker is also running, so a re-keyed object is visible to
     both. The lane-ON write is attributed to the in-process consumer by (a) the
     consumer's own trace-scoped log line "asset_ingestion_record_handled
     outcome=processed" from endpoint_asset_ingestion modules, (b) a
     consumer-EXCLUSIVE reingest driven by a manual SQS S3-event sent to ONLY the
     endpoint-asset-ingestion queue (same key, outcome=processed again,
     idempotent), and (c) the consumer's own Prometheus counters
     (asset_ingestion_* labelled tenant_schema=tenant_b_prdct14239), quoted below.
